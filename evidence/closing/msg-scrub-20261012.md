# Commit-message scrub of the unpublished range, and the pre-flight made standing

Owner ruling 2026-10-12, the first of four items: scrub the host-path shapes out of the commit messages that have
never been published, then push. The ruling said two messages; the measurement said three, and this face records
the measurement rather than the estimate. Authorisation cited by shape, not by restatement: "rewrite only the local
commits that were never pushed" - the same authority the morning's history fix used, and no wider.

## 3. Verification - one ruler, run on both sides

`python ci/face_preflight.py --messages <range>` is the ruler. It was not edited between the two runs below, so the
difference is the scrub's doing and not the gate's.

| range | checked | blocked | OUTCOME |
|---|---|---|---|
| `bd0c430..refs/backup/pre-msg-scrub-20261012` (the pre-scrub chain) | 11 | 3 | `RED` |
| `bd0c430..HEAD` (the rewritten chain) | 11 | 0 | `CLEAN` |

Structural proof, from the file-based comparator (`msg_rewrite_verify.py`, kept outside the tree because it names
needle classes):

```
trees_differing=0 stamps_differing=0 messages_changed=3
cr_bytes_new=0 non_utf8_new=0 path_tokens_old=5 path_tokens_new=0
OUTCOME=GREEN
```

`trees_differing=0` is the load-bearing one: every rewritten commit points at exactly the same tree object as its
predecessor, so the pass moved metadata and no file. `stamps_differing=0` covers author name, author email, author
date, committer name, committer email and committer date - a rewrite that silently re-dates commits would be the
second-most-common way to fake an audit trail, and it did not happen here. `cr_bytes_new=0` is the guard against the
failure this pass actually produced on its first attempt, see §4.

Pairing method is recorded because it was wrong once: the first comparison sorted both chains by commit hash and
zipped them, which pairs unrelated commits and reported 10 changed messages where 3 had changed. Chain position
(`git rev-list --reverse`) is the only correct key, since every commit in a linear range has exactly one successor.

## 4. Four defects this pass caught in itself

**(a) The first rewrite produced byte-identical trees but DOS line endings in every message.** A message filter that
writes through a text-mode stdout on this host translates `
` to `
` twice over; the commit contents would have matched while the metadata changed shape, and
the visible symptom is that `git log --format=%B` output stops matching the pinned digests. The rollback was done by
pointing the branch back at the backup ref and writing each tracked face from its HEAD blob bytes (245 files), not
by a checkout - a checkout under `core.autocrlf=true` re-smudges LF to CRLF and re-contaminates the tree, which is
the same trap in the other direction and cost a batch of readings earlier the same day. The scrubber now speaks
bytes in both directions.

**(b) The scrubber's own longest-first rule labelled the wrong tree.** Its first pattern made the working-copy
segment optional, so the read-only sibling checkout matched the working directory's phrase. Had it gone out, the
message would have said that a lane rewrote 129 faces "inside this seat's own working directory" - a false claim
about which tree was violated, in the one place the project keeps its record of having violated it. Found by reading
the rewritten line rather than the replacement count (counters had read `replacements=1 residual=0`, which is a
green reading of a wrong sentence). Fixed by requiring the distinguishing segment, and the first pass was discarded:
the branch was moved back to `refs/backup/pre-msg-scrub-20261012` and the range re-rewritten, which is why §2's
table lists old hashes that differ from an earlier draft of this record.

**(c) A residual check run through an inline heredoc was a false negative.** Patterns passed to `python - <<PY` on
this host lose their doubled backslashes, so a class written `[\\/]` arrives as a slash-only class: the check found
zero hits because it had stopped looking for the backslash spelling, which is the dominant spelling in Windows paths
and the whole reason the disclosure leg carries escaped forms. That reading is withdrawn. Everything in §2 and §3 is
measured by file-based rulers - the scrubber's own residual pattern and `ci/face_preflight.py` - each of which has a
red arm for the backslash spelling.

**(d) The gate's message pattern had no left boundary.** `https://host/x` ends in `s://host`, and without a
lookbehind a drive-letter rule reads the tail of any URL as a Windows path. Measured over the whole committed history
(138 messages), exactly 1 message was flagged for URL text alone - the one citing this project's own published
address. A rule that condemns the project's public URL is a rule the next window widens by hand, so the boundary
went into the pattern rather than into an exception list, and arms M3 (URL-only text passes) and M4 (a real
drive-letter path behind a slash, and one with backslashes, are both still refused) pin both sides. The fix changed
none of the counts in §3: the pre-scrub range still reads `blocked=3`. `--selftest` reads `arms=13 passed=13`.

One arm failed on its first draft for the reason arm failures usually do: its fixture path had one-character
segments, below the pattern's two-character floor. The fixture was wrong, not the rule, so the fixture was corrected
and the rule was left alone.

## 5. What cannot be changed, and is therefore only recorded

The published segment (`git rev-list bd0c430`, 127 commits) carries **10 messages with 11 drive-letter path shapes**,
in `f67eeb9 0186b8e 98d549c aa793da a00ee80 b6f863c 8900037 d6994fd e3c1acd 1d0e2ba`. These are already on the
published side; the standing order forbids rewriting published commits, and a force-push would rewrite other
people's clones rather than this file. They stay as they are and are named here so that a stranger who greps the
public history finds the admission before the finding. The three already-published identity-wording commits are a
separate, already-accepted class and are not counted in these ten.

## 6. The standing instrument (owner item 2)

The scrub is a one-off; what stays is the answer to "how does this not happen again".

| face | what it does |
|---|---|
| `ci/face_preflight.py` | one ruler, four modes: `--staged` (lines this commit would add), `--paths` (named faces), `--message-file` (one draft message), `--messages <range>` (a set of commit messages). It imports the disclosure leg's needles and routing function instead of holding a second opinion, and prints class, line, length and character classes - never the path bytes. 13 arms, both sides |
| `ci/hooks/commit-msg` | the enforcement point for metadata. A message cannot be edited after the push, so the only moment it can be judged is when it is written. The hook holds no patterns of its own and calls the ruler. `.git/hooks` is not a tracked face, so installation is a command, not a file: `cp ci/hooks/commit-msg .git/hooks/commit-msg && chmod +x .git/hooks/commit-msg` |
| `.github/workflows/matrix.yml` | runs `face_preflight --selftest` and `process_leak_scan --selftest` so the rulers cannot rot quietly, and runs the message mode over the range each push adds |

Both sides of the hook were executed, not asserted: with the hook installed, a draft message naming a
`<drive>:\<sep>\Users\…` shape returns rc=1 and `OUTCOME=RED … a push makes these permanent`, and an ordinary
sentence about legs and denominators returns rc=0 and `OUTCOME=CLEAN`.

The CI job deliberately does **not** scan the whole history with the message mode. §5 is already RED and is not
changeable under the standing order, so a history-wide leg would be permanently red from the day it landed and would
be ignored by the second week - the standard way a gate dies. It scans the commits a push adds, which is the same
set the hook had the chance to refuse.
