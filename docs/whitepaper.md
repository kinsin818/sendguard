# sendguard · 文件名体检报告

同一个文件名能不能存，取决于三件互不相干的事：**你用哪门语言数它、你把它放在第几层目录、以及收文件的人用什么系统。**

这份报告的全部结论，每一行都带一条能重跑的命令。跑出来不一样，就是这份报告错了——`docs/expected-summary.md`
里"预期 vs 实测"逐行对照已经先记了三条我们自己预测错的行（见 §5）。

**文中所有计数是 2026-10-11 05:1x +0800 的读数，不是终态。**各门仍在补格，重跑下面的命令会以同一条
`OUTCOME=` 行覆盖这些数字；一个数字对不上，就以命令输出为准、以本文为错。

复现入口：

```
git clone <本仓> && cd sendguard
python ci/selftest.py --scratch-root ../sg-st      # 14 条臂，闸必须既能判红也能判绿
python ci/equality.py                              # 六门 × 冻结规范：判定字段是否逐字节相同
python ci/gap_report.py                            # 每门还差哪些格，按名字列出来
python ci/expected_summary.py                      # 预期 vs 实测，含"没跑"和"接不上"两种诚实状态
```

## 1. 这份东西是怎么造出来的

一份冻结规范（20 条陷阱 + 5 个控制格 + 5 个盲样本 + 每语言钉死的 API 入口，样本一律 hex 存字节），
六个互不可见的实现各写一门：TypeScript(Node 24 去类型)、Python、Go、Java、C#、Rust。
**没有跨语言调用，没有共用工具函数，没有互相抄。**判定只看一件事：同一格上，六门交付的报告字节是否相同。

规范的哈希在任何一门跑之前公布（`spec/FROZEN.md`，8 件产物）。期望表由一个既不写门也不写骨架的实现
先写好封存（`spec/expectations.sealed.md`），六门全跑完才打开对照——这一条是为了抓第六种失败：**六门
一起读错同一句话**。

## 2. 六门一致的地方（这才是可交付的证据）

**先说清楚：本文件所有计数以 `docs/STATUS.md` 为准，那是从闸的输出文件生成的；重跑一次 `python ci/refresh_all.py`
就会更新。下面这组数字是 2026-10-11 10:19 +0800 的读数。**

在当前提交上，44 个必交格六门全都答了，全都可比；其中 **24 格没有任何两门的判定字段互相冲突**：

```
python ci/equality.py | grep cells_with_no_verdict
```

- 长度族：`len/T17` 与 `len/T18` 在 78/120/200 三个档位的**普通路径形式**六门全同（6 格）。
- 归一化族：`trap/T06` emoji、`T07` NFD、`T08` NFC、`T09-m1`/`T09-m2`（NFC 与 NFD 同目录共存）、
  `T12` 双向文字 U+202E、`T13` 零宽 U+200B、`T15` 控制字符、`T19-m1` 全角、`T19-m2` 韩文자모、`T20` `--force.txt`。
- 非法字符 `trap/T03`（`a<b.txt`）：六门现在全说"非法"（此前一门说合法，是因为它先加了长路径前缀再问）。
- 五个盲样本 `blind/B1..B5`（挑名字的人没参与造题）：六门判定一致。
- 一个控制格 `ctrl/T-CTRL-ASCII`。

值得停一下的是这一组的构成：**六门全部一致的，正是归一化族与普通路径下的长度族**。一份规范被六份互不可见的
实现读过之后，这两族一个例外都没有——这是"规范写得清楚到能被独立复现"的证据，不是语言味的巧合。

## 3. 六门不一致的地方（这才是要卖的东西）

剩下 20 格产生 54 条判定冲突。它们不是散布在各处，而是集中在三类机制上：

```
python ci/equality.py | grep VERDICT-DISAGREE
```

| 陷阱 | 六门的回答 | 一句话 |
|---|---|---|
| `T01` `CON.txt`、`T10` `CON`、`T11` `COM1.log` | 四门"合法、写成功、盘上没有条目"（幻影），两门（Go、Rust）直接"非法"；字节数上 0 / 28 / 缺记三种都有 | 同一个保留名，"能不能建"取决于语言的调用约定；"建成功了"甚至不等于"盘上有" |
| `T04` 结尾点号、`T05` 结尾空格 | 四门"合法且落盘被改名"，两门"非法"；一门说名字没被改；一门报盘上 0 字节而四门报 28；一门同时记请求 6 与落盘 5 | 尾点/尾空格剥离不是 Windows 的属性，是你调的那个 API 的属性 |
| `T14-m1` `PRN` | 五门各有说法，一门直接给 `unknown` | 保留名是否"存在"还取决于这台机器插了什么设备（本机实测：`PRN`/`LPT9` 无设备后盾，`CON`/`NUL` 有） |
| `T16` zip 打包回读 | 同一个名、同一份载荷：三门 28 字节、一门 296、一门 292 | 压缩库在"要不要置 UTF-8 标志位"上分三派，Mac 的包到 Windows 变形就是这里 |
| 长度族六格（全部是 `\\?\` 扩展形式那一侧） | 三门 `roundtrip_ok=True`，一门 False（它在 parse 层就拒绝了这个前缀——**这个"拒绝"只对它实际跑过的那枚 JVM 成立**，见下一行）；一档上另一门 `enum_to_stat_agrees=False` | **普通路径下六个档六门全同，加了 `\\?\` 就分歧**：长路径不是"开一个注册表开关"，是每个可执行文件的清单 + 每种调用方式 |
| `\\?\` 那一侧的门内分歧（Java，同一枚编译好的类） | 用 Temurin 17.0.17（也就是已录格子上跑的那枚 exe）启动：`Paths.get`/`Path.of` 抛 `InvalidPathException`（`Illegal character [?] at index 2`），同一次运行里 `new File(String)` 接受；换成 Temurin 21.0.6 拿同一个 class 再跑：`Paths.get` 接受并把前缀吃掉（`toString()` 已不含 `\\?\`） | **分歧可以落在同一门语言的两个运行时之间**——所以"用哪种语言写的"这个问题问得不完整，体检报告必须连 JVM 版本一起上报，否则客户端装的是哪一版没人知道 |
| 控制格自检的出处 | 六门 30 个控制格全部盖了自检通过标记，**但没有一格写着"这个结论是哪条命令跑出来的"**——`spec/` 里没有这个字段，所以这不是某一门的疏忽，是契约的空位（量出来的：`python ci/validate_cells.py` 的控制格栏） | 校准格校准出来的不是 Windows，是各门愿不愿意对自己的结论负责；而"负责"目前最多只能写到 `true` 这一格字 |
| 三个控制格（`T-CTRL-PARSE`、`-ILLEGAL-CHAR`、`-NAMETOOLONG`） | 机制分类上 Java 给 `unknown`，其余五门给同一个具体类；`T-CTRL-CANON` 上只有一门敢分类 | 校准格校准出来的不是 Windows，是各门愿不愿意对自己的结论负责 |

这些行没有一行需要解释谁对。**它们就是产品**：任何一个用单一语言写成的"发件前体检器"，都会在同一台机器上
对同一个文件名给出与另外几门不同的答案；把检查建在其中任何一门之上，都是在赌客户端和收件人恰好没被那一层
的策略坑到。

一条诚实的限定：**13 格的"合法性判定"字段被记为弃权**（某一门走的是别的答案通道，比如一门在长度格上没有
OS 级合法性渠道），闸只把那一个字段摘掉，其余判定字段照比；弃权名单由 `docs/STATUS.md` 逐格列出。这不是把
分歧藏起来——藏起来会让冲突数变少，而这里少掉的那一格（`T03` `a<b.txt`）是被数据解决的：一门改了它的探测
方式之后，六门现在都给"非法"。

## 4. 长度这件事上，两个尺度不是一回事

`T17`（全路径逼近 260 码元）与 `T18`（单个组件逼近 255）必须分开问，而且必须 `\\?\` 开/关各问一次。
这一点现在有数据了（此前一度没有：六个门填了六种不同的组件内容，闸只能整族排除）：规范补齐了
`len_fill`（单码元 U+0061 重复到指定长度）之后重跑，结果是**普通路径三个档位六门全同、扩展形式三个档位
全部有冲突**——见 §3 长度族那一行。本机 `LongPathsEnabled=0`，是否放行还取决于**每一枚 exe 自带的清单**，
这是按可执行文件生效的属性，不是按语言生效的属性。

长度一律记 `码点 / UTF-16 码元 / UTF-8 字节` 三元组，禁止写成单个数字；各门二分出来的临界值另记
`len_ceiling`，不与名字长度混写。多字节档位（emoji、CJK）作为额外格保留——"按码元判还是按字节判"的
故事在那里，而不在这一份比较里。

```
python ci/length_report.py && cat docs/length-family.md
```

那一行的原始读数不靠复述：`impl/java/tools/ext-path-of-repro.txt` 里同一枚编译好的 class 用两版 JDK 各跑一趟
（两次 `run_rc=0`、11 个 TAG）。17.0.17 那一趟（已录格子就是在它上面跑的）里 TAG 3 是三行彼此矛盾的读数——
`Paths.get` 抛 `InvalidPathException`（`Illegal character [?] at index 2`）、`Path.of` 同抛、而同一趟里
`new File(String)` 是 `OK`、`isAbsolute=true`；21.0.6 那一趟同一个 TAG 给 `Paths.get -> OK`，`toString()`
已经把前缀吃掉。文件里还留着第三行对照：PATH 上那枚 Oracle 1.8.0_31 **没有**被拿来跑——这个 class 调的是
`Path.of`（JDK 11 才有的 API），1.8 只会回 `UnsupportedClassVersionError`，那是启动器的事实，不是一次测量。

```
cat impl/java/tools/ext-path-of-repro.txt
```

## 5. 我们自己错在哪（原始输出照印）

- **预测错**：封存期望表在 `T01 CON.txt`、`T10 CON`、`T11 COM1.log` 上预测读结果为 `hang`；
  五门交回 `not_applicable`（根本没落盘，就没有可读的那条腿），一门交回 `eof`。
  ```
  python ci/expected_summary.py | grep CONTRADICTED
  ```
- **量错**：等值闸一度报"29 格全红"。逐格回读发现四门在同一格上记的是**同一个事实的四种写法**
  （hex 与明文；长度三元组的 dict、`15/15/15`、`[15,15,15]` 与被省略）。闸把写法当成分歧，
  就会把真正值得看的五行埋掉。修的是闸，不是门。
- **发布过一份错的必交清单**：第一版 `spec/cells-required.json` 来自一次错解析，只看见 20 条陷阱、
  漏掉控制格与成员分裂。文件里按名字撤销了自己，下游一律以重新生成的版本为准。
- **一把只会说"不"的闸**：`ci/selftest.py` 现在有 21 条臂，其中六条专门证明它会放行——
  `green-identical`、`probe-difference-is-data`、`sub-identity-separates`、`alias-folds-spelling-drift`、
  `same-name-two-encodings-agree`、`coverage-green-still-passes`。
  ```
  python ci/selftest.py --scratch-root ../sg-st | grep -E "arms=|OUTCOME="
  ```
  同一条命令还要换两块盘各跑一次（scratch 分别放 C: 与 D:），两次都得 21/21——理由见下一条。
- **后来又抓到三件自己的量具毛病**，都属于"看起来在尽职、实际在骗人"那一类，逐条原始输出与修法记在
  `docs/FINDINGS-rev6.md` 的 M6：
  1. 一长串字母 `a` 本身就是合法 hex，于是"像 hex 就解码"把两门写成的文本读成三个 `0xAA` 字节，
     同一个名字被判成冲突。现在一个名字按"它可能是哪几种意思"的集合求交比较，靠这一步才判成一致时
     明打印 `NAME-CROSS-FORM-AGREE`。
  2. 自检拿两颗假门跑闸，而闸的结果文件路径写死在证据目录里：**每一臂都把真结论覆盖成假结论，而自检
     自己全绿**。现在假门只能写进自己的临时目录，出表的工具还要求结果文件的来源必须是本仓 `results/`。
  3. 临时目录落在另一块盘时 `os.path.relpath` 抛异常，闸崩在 rc=1——而 rc=1 正是本闸"六门冲突"的代码。
     同一套臂在 D: 全过、在 C: 假红 8 条。**量具崩掉会被下游读成测量结果，这是本项目最贵的一类错。**

- **一条"看着两面都验了"的列，一天里四次量错同一件事**：`ci/delivery_form.py` 是今天下午加的量具，回答
  "客户到底拿到什么"。它一天错了四次，四次是同一个形状——**数字在两台机器上一致，可没有任何东西问过第二个
  主体它的文件集合对不对**：
  1. 先按磁盘上有什么来报工件，于是某道 lane 没提交的 scratch 被当成"交付物有多大"：冷克隆读 3796 B，
     工作树读 3834 B。
  2. 改成读 `git ls-files` 之后**看起来修好了**——因为分隔符写成了字面量 `"SEP"`，61,776 个字符被当成集合里
     的一个元素，过滤器把每个文件都判成未跟踪；而"六门全 0"恰好和克隆一致。我把这次一致当成修好的证据写进了
     提交说明，它其实是故障本身的症状。
  3. "被忽略的未跟踪文件"那一列依赖盘上有没有这个文件：同一枚 commit，工作树 `untracked_ignored=14`、克隆
     `12`。这一列已经从发布面挪进运行行——发布面必须只说仓库的事。
  4. `glob` 保留模式里写的斜杠，返回 `D:\repo\impl/java/build\CellProbe.class`，与纯反斜杠的跟踪集永不相等，
     于是 6 枚已提交的 `.class`、`impl/python/sg_run.py` 和 7 份 TypeScript 源文件全被判成未跟踪，
     "没有任何一门提交编译产物"这句话进了发布面和提交说明。
  第 4 条不是我看出来的：给它加了一把**不由它自己实现**的见证器（`git_artifact_paths`，让 git 的 pathspec
  再数一遍），`self_check` 一见两边不一致就拒绝发布，第一次跑就打印
  `this leg's file classifier kept 6 tracked artifact(s) and git's own pathspec names 0`。见证器随后也错过一次
  （用 `fnmatch` 把 `**` 当成 `*`，把 `build/**/*.class` 变成两段模式，六枚真文件一枚都不认），所以模式转换器
  `pattern_to_regex` 自己也有了双向臂 A18。这是本项目第二次不得不去验"用来验的东西"。
  ```
  python ci/delivery_form.py --selftest | tail -1     # arms=18 passed=18
  python ci/delivery_form.py                          # instrument_problems=0 tracked_paths=1167
  ```
  现在的表（`arms=18 passed=18`、`instrument_problems=0`，且在克隆 `d6994fd` 的冷树里逐字节一致）：
  **14 个跟踪工件、310,141 字节**——java 6 枚 `.class` 共 86,825 B、python `sg_run.py` 81,900 B、typescript
  7 份 `.ts` 共 141,416 B；`csharp`、`go`、`rust` 三门不提交任何构建产物；安装包 0 枚；不装编译器今天就能跑的
  文件只有一枚 `tool/check.py`（81,759 B，只依赖 Python 3 标准库）。
  两条常设规矩：**分类文件的量具必须由一个不由它实现的枚举复核**——分母只证明它读了多少，不证明它读对了哪些；
  **过滤器必须有一臂证明它会放行**（A5"已跟踪工件必须活过过滤"），因为其余每条臂都能被一个"把世界全丢掉"的
  过滤器满足。

- **把"没人反对"当成"都答过"**：这份报告一上午都在引用"44 格里 24 格无判定冲突"。那句话是真的，但它把
  **沉默算成了一致**。12:05 重测：24 格里只有 **4 格**是六门把十个判定字段全部填了的格子（恰好是普通路径的
  `T17`/`T18` 两档），另有 121 个字段格是某一门没填、10 个字段格六门都没填。现在闸在同一行 `OUTCOME=` 里
  同时印 `cells_fully_recorded_and_identical=4` 和 `verdict_not_recorded_pairs=121`，两个数不许单独引用，
  逐门逐字的覆盖率表在 `docs/coverage.md`。
  ```
  python ci/equality.py | sed -n '/coverage (who answered what)/,$p'
  ```
- **我自己的两把尺子量的不是同一件事**：同一分钟里 `ci/validate_cells.py` 报"557 格全部合规"，闸报"121 格空白"，
  两句都对。往下查不是门的问题，是规范的问题——`spec/schema.json` 必填的 17 项里**不含闸用来判定的 10 个字段中的
  9 个**，其中 `phantom`、`name_mutated`、`len_triple`、`name_landed_as` 连"已文档化字段"都没进。
  换句话说，"六门判定逐字节一致"这句话一直建立在"这些字段没人被要求回答"的前提上。修法是把差集公开印出来
  （`docs/cell-validation.md` 现在有一张逐门省略计数表），并把"哪些空白是合法的"交回契约本身——
  下一轮契约要拍的事，维护方不擅自改封存件。
  ```
  python ci/validate_cells.py | tail -1 && sed -n '/does not require/,/^## What this/p' docs/cell-validation.md
  ```

- **"一份冻结规范"这句话此前只在文件头里写着，没人拿去比过记录**。每一格其实都带着一枚规范指纹，但整条流水线
  从来没把它和清单上的当前指纹对过一次。一查就查出：**被比较的 264 条记录里 27 条带着上一轮指纹**（全是同一门的
  陷阱格／盲样本格／入口格，那门在 06:11 重封存之前没重跑）。新加的腿不给我圆场的空间：它先找出哪一次提交的
  `spec/cases.yaml` 哈希等于那枚旧指纹，再把那一版与 HEAD 逐行求差、从差的行反查所属的 case（一个 case 是一整块，
  只读改动那一行会漏），最后把差集与那 27 格的 case id 求交——**差集只碰 `T17`/`T18`，27 格里一个都没有**，
  所以"问的是同一道题"这件事现在是量出来的，不是我说出来的。以后只要差集真碰到某个带旧指纹的格，这条腿直接退 1。
  ```
  python ci/spec_drift.py && sed -n '/Per older fingerprint/,/^## What/p' docs/spec-drift.md
  ```

## 6. 现在做到哪一步，没做什么

已做：六门全部在 Windows x64 本机出数，**44 个必交格六门全答、全部可比**；闸、自检、矩阵、缺口表、
长度族披露、预期对照表、状态表、证据表全是生成物，不手填，一条 `python ci/refresh_all.py` 全部重算。
